# Android smoke: UI и миграция Room

> **Итог:** [зелёный Android-прогон 27.10.2026](ANDROID_SMOKE_RESULT_2026-10-27.md), коммит `75bd09d`: 8 instrumentation-тестов, без ошибок и пропусков.

> Расширение сценария и границ проверок описано в [FREE_SPACE_FLOW.md](FREE_SPACE_FLOW.md). [Новый прогон 12 Android-тестов завершён успешно](FREE_SPACE_FLOW_RESULT_2026-10-27.md); прежний результат восьми тестов относится к прежнему коммиту.

План runtime-проверки после [штатного CI этапов 1–2](CI_VALIDATION_2026-10-27.md). Факт успешного выполнения фиксируется отдельно по run/SHA; наличие этих тестов само по себе не означает, что они прошли.

## Среда и границы

- Одноразовый CI-эмулятор Android 15 / API 35, `google_apis`, x86_64, KVM.
- Устанавливается настоящий Debug APK с production Hilt/Application/Compose-кодом.
- Каталог AVD изолирован через `ANDROID_AVD_HOME`, но `ANDROID_USER_HOME` не меняется: он также влияет на debug-keystore Gradle. Перед запуском сверяются SHA-256 сертификатов target/test APK; signature check Android не обходится.
- Shizuku/Root не подключаются. Физический телефон, другие API/OEM и Release APK во время этого smoke не проверяются.
- Скрипт отказывается работать вне GitHub Actions или при наличии уже подключённого ADB-устройства. Для Gradle задан serial созданного эмулятора.
- Тестам очистки выдаётся all-files access только на одноразовом эмуляторе. Они создают собственные UUID-каталоги в Download. Подтверждение удаления допустимо только для явно выбранного синтетического fixture; другие файлы не выбираются. В конце убираются только известные fixtures, без рекурсивного удаления чужого содержимого.
- Room-тесты создают отдельную БД со случайным именем; реальные системные настройки не изменяются.

## Обязательные сценарии

### `app:BasicSmokeTest` — 8 тестов (актуальный сценарий «Освободить место»)

1. Холодный запуск, BASIC-режим и переход по всем пяти разделам.
2. Сохранение выбранного раздела при пересоздании Activity.
3. Accessibility-аудит: автоматическое массовое отключение недоступно, значение списка служб после проверки не изменено.
4. Сканирование синтетического `.tmp`, явный выбор, план, выключенная кнопка без согласия, пересоздание Activity и отмена без удаления.
5. Возврат из настоящих настроек доступа обновляет разрешение без автоматического поиска.
6. Удаляется ровно один выбранный синтетический файл; соседний не затрагивается.
7. Изменённый после подготовки файл пропускается с честным результатом.
8. Поиск/фильтры не расширяют и не забывают явный выбор.

### `core:vault:VaultMigrationInstrumentedTest` — 4 теста

1. Реальный Android SQLite v1 → Room v2: схема валидируется Room, старые ID/статусы/JSON и повреждённый payload не теряются; база открывается повторно.
2. Legacy и corrupt записи после миграции не вызывают executor при попытке отката.
3. Записанный `STARTED`, пользователь и boot ID сохраняются после закрытия и повторного открытия базы.
4. Частичный неуспешный откат сохраняет статусы отдельных шагов, не становится успешным после повторного открытия.

Fixture v1 воспроизводит таблицу исследованной версии. Это проверка настоящего `MIGRATION_1_2` и сгенерированной Room schema validation на Android, но не обновление пользовательской установки со всеми её данными и ключом подписи.

## Запуск

В существующем workflow `scripts/ci-build.sh` после unit-тестов и сборки APK вызывает:

```bash
bash scripts/android-smoke.sh
```

Gradle компилирует настоящие instrumentation APK:

```bash
./gradlew :app:assembleDebug :app:assembleDebugAndroidTest :core:vault:assembleDebugAndroidTest --stacktrace --no-daemon
```

Собранные APK устанавливаются на созданный AVD. Их зарегистрированные компоненты `androidx.test.runner.AndroidJUnitRunner` определяются через `pm list instrumentation` и запускаются обычным `adb shell am instrument -w -r` с указанными тестовыми классами. Ни тесты, ни assertions не заменяются. Такой запуск не зависит от дополнительного host UTP runtime, загрузка которого остановила первый `connectedDebugAndroidTest` сетевой ошибкой после успешного запуска эмулятора.

`instrumentation-to-junit.py` переводит настоящий протокол AndroidJUnitRunner в XML. Нужны совпадающие start/finish записи каждого теста, объявленное количество тестов, финальный код runner и отсутствие crash/abort. Просто строка `OK` не считается доказательством. Исходные протоколы сохраняются рядом с диагностикой.

Результаты отделены и от JVM XML, и от отчётов Gradle connected:

```bash
python3 scripts/summarize-junit.py --kind android --android-source adb-smoke --min-tests 12 \
  --require-module app --require-module core:vault --fail-on-skip
```

Нет устройства, нет XML, отсутствует один из модулей, есть пропуск/ошибка или менее двенадцати тестов — это ошибка, а не «зелёный smoke». Отчёт публикуется в job summary и CI-аннотациях. Для parser/gating есть отдельные Python self-tests; они не засчитываются как Android-покрытие.

Логи, параметры устройства и финальный screenshot сохраняются в `build/android-smoke/` на runner. Действующий workflow не умеет выгружать дополнительные артефакты; предложение с ними находится в `docs/ci/github-actions-build.yml`. Не следует считать screenshot просмотренным или доступным локально, если он не был отдельно получен.

## Что остаётся после успешного smoke

- TalkBack с реально включённой службой, большой шрифт и визуальная проверка экранов.
- Реальный Binder Shizuku, Sui/su, потеря прав и неоднозначное завершение привилегированной команды.
- Другие версии Android, OEM, secondary user/work profile, восстановление после смерти всего процесса/потери питания.
- Проверка подписи и обновления настоящего APK, не только схемы БД-fixture.

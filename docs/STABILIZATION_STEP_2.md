## 1. Что теперь означает результат операции

| Ситуация | Поведение |
|---|---|
| Значение действительно отсутствует | `StateReadResult.Missing`; допустимо как исходное состояние Settings |
| Нет доступа, неподдерживаемый/неполный ответ | `Unavailable`, а не `null`, `ENABLED` или `default` |
| Команда не отправлялась | `CommandCompletion.NOT_STARTED` |
| Процесс команды завершился | `EXITED`, с отдельной проверкой exit code |
| Таймаут, потерянный транспорт, непонятное завершение | `UNKNOWN`; немедленный откат не запускается |
| Поддерживаемое изменение успешно | Команда завершилась успешно **и значение прочитано обратно** |
| Ошибка после частичного изменения | Проверяется и восстанавливается также неуспешный шаг, не только предыдущие |
| Откат завершён | Для затронутых шагов подтверждены исходные значения; невыполненные шаги не трогаются |
| Третье значение или более новая конфликтующая запись | Откат отказывается перезаписывать состояние |

Чтение сохранённого значения не доказывает физический эффект: записанные `120 Hz` не гарантируют 120 Гц, параметры Private DNS не доказывают доступность/фильтрацию резолвера. Эти проверки остаются задачей конкретных сценариев.

## 2. Исполнитель команд

### Изолированное выполнение и ограниченное ожидание

- Мутации Root больше не используют общую очередь `Shell.cmd(...).enqueue()` libsu. У каждой команды свой процесс `su -c`; libsu остаётся для обнаружения/запроса Root.
- Shizuku/Sui сохранены как отдельный транспорт. Проверяется доступ и ожидаемый UID; после потери сервиса нет автоматического перехода на незапрошенный `su`.
- Внутри привилегированного процесса проверяется `id -u` перед пользовательской командой: UID 2000 для ADB/Shizuku, UID 0 для Root.
- `BoundedProcessRunner` ограничивает ожидание запуска, Binder-preflight, завершения и чтения вывода. Зависший `Process.waitFor()` не блокирует вызывающий coroutine бесконечно.
- Вывод ограничен по размеру, но потоки продолжают дренироваться, чтобы переполненная pipe не остановила процесс. Наружу возвращаются отдельные копии вывода.
- Если preflight вернулся после таймаута/отмены, он не должен начинать новую пользовательскую команду. Если сам запуск уже был отправлен, поздно полученный процесс получает запрос остановки.
- Отмена coroutine пробрасывается, а не превращается в успешный/пустой результат.

**Ограничение:** остановка процесса запрашивается, но уничтожение всех потомков и завершение работы системного сервиса не объявляются доказанными. Поэтому неизвестный результат не компенсируется вслепую.

### Сохраняемый барьер после неизвестного завершения

Перед потенциально изменяющей командой синхронно записывается ticket. Он очищается только при известном завершении или доказанном отсутствии запуска. При `UNKNOWN`, смерти процесса приложения или ошибке журнала новый изменяющий вызов не стартует.

- Перезапуск приложения или Shizuku сам по себе не снимает неизвестность.
- Для подтверждения новой загрузки используется **UUID ядра `/proc/sys/kernel/random/boot_id`**. `BOOT_COUNT`, часы и факт открытия приложения не используются как доказательство остановки старых процессов.
- Если обычному процессу недоступен boot ID, выполняется отдельный фиксированный read-only запрос через уже разрешённый Shizuku/Root. Он не может содержать пользовательскую shell-строку и не изменяет систему.
- Отсутствие достоверного boot ID блокирует новые системные мутации, а не создаёт выдуманную метку.
- Пустые preferences после ошибки чтения существующего XML не считаются свежим пустым журналом: формат содержит явные `version`, `idle`/`pending` и проверяемый ticket.
- Повреждённый журнал не сбрасывается автоматически. При этом штатное чтение информации остаётся отделено от исполнения изменений.

### Read-only запросы отдельно

`SystemReadQuery` — закрытый набор фиксированных/валидируемых запросов: свойства устройства, диагностические dumpsys, список пакетов выбранного пользователя, AppOps и др. Они могут работать в BASIC и при закрытом барьере мутаций, не очищая этот барьер. Свободная shell-строка на этот путь не принимается.

Паспорт устройства, чтения Fixer и AppOps переведены на этот контракт. Ошибка/обрезанный ответ диагностики больше не разбирается как пустое «здоровое» состояние. Обычные файловые сканеры имеют отдельные ограничения покрытия — они не стали привилегированными от подключения Shizuku.

## 3. Проверяемые операции StateVault

Поддержаны типизированные изменения:

- `Settings`: отдельные значения и отсутствие ключа, включая различие между отсутствием, пустой строкой и буквальным `"null"`.
- Состояние пакета: **enabled-setting и suspension отдельно**, без подмены `DEFAULT` на `ENABLED`. Сохраняются UID и `lastUpdateTime`; обновление/переустановка пакета не дают автоматически применить старый package-state откат к новой версии.
- AppOps отдельного пакета: только однозначно прочитанные поддерживаемые режимы. Смешанный UID/package-ответ не подставляется в package-откат как `default`.

Дополнительно:

- Используется Android user текущего процесса, а не безусловный `--user 0`.
- Запрос целиком проверяется до первой мутации. Повторяющиеся ресурсы, неподдерживаемые shell-шаги, недопустимые режимы и непереносимые через CLI значения отклоняются.
- Settings-строки с NUL или объёмом более 16 KiB отклоняются, в том числе если таким является исходное значение: нельзя обещать откат, который невозможно передать транспорту.
- Уже совпадающее состояние не перезаписывается и не даёт откату право отменять последующие чужие изменения.
- Проверяются статические критичные пакеты, собственный applicationId, домашние экраны, текущая клавиатура и включённые службы доступности. Проверяется и предполагаемая обратная запись. `DEFAULT` не объявляется безусловно безопасным для критичной роли.
- Если безопасный обратный шаг заранее невозможен, такое изменение не выдаётся за обратимое. Для одностороннего ремонта потребуется отдельный сценарий с явным согласием.

## 4. Журнал шагов и восстановление

До начала изменения сохраняются before-state, Android user, boot ID, весь список операций и `PLANNED` для каждого шага. Перед командой записывается `STARTED`; перед обратной командой — `REVERTING`. Состояние и журнал шагов обновляются одной записью Room.

Основные переходы:

```text
PREPARED → APPLYING → ACTIVE
               ↓
         ошибка с известным завершением
               ↓
         ROLLING_BACK → ROLLED_BACK
               ↓
             FAILED → повторная проверка/восстановление

таймаут / отмена / прерванная незавершённая команда → RECOVERY_REQUIRED
повреждённые данные → CORRUPTED (без автоматического выполнения)
```

- После сбоя остаётся информация, какие шаги ещё не запускались, какие уже завершены и какие неизвестны.
- Неизвестные команды не вызывают немедленную компенсацию. Перед дальнейшим восстановлением нужен подтверждённый новый kernel boot ID.
- При повторном откате уже отменённые шаги не выполняются заново.
- Более новая запись с тем же ресурсом не даёт старой перезаписать её значения; порядок определяется ID записи, не часами телефона.
- Массовый откат учитывает `FAILED`/прерванные записи, останавливается на первом сбое и возвращает количество восстановленных, ошибочных и не начатых записей.
- Известная завершённая ошибка отката сохраняется в истории, но не запирает навсегда независимые инструменты. Неопределённые/прерванные операции и повреждение журнала остаются блокирующими.
- Обработчик отмены перечитывает последнюю сохранённую запись: внешняя функция не может затереть более свежий журнал внутреннего отката своей старой копией.
- Повреждённые исходные payload не перезаписываются через пустую domain-модель даже при последующей ошибке.

Справочный снимок девяти Settings теперь явно **не является полным бэкапом или автоматическим откатом**: он имеет отдельный статус и доступен для просмотра/экспорта.

## 5. История и миграция

Room-схема: **1 → 2**, формат нового журнала: **1**.

- Миграция только добавляет поля: `journalVersion`, `userId`, `bootId`, `stepsJson`, `lastError`.
- Убрана `fallbackToDestructiveMigration`: отсутствие подходящей миграции не должно молча уничтожать историю системных изменений.
- Старые ID, операции, статусы и JSON сохраняются.
- Исторические записи без подтверждённого before-state/журнала шагов показываются как `LEGACY_UNVERIFIED`, включая старый неподтверждённый `ROLLED_BACK`. **Они не выполняются автоматически.** Старый статус остаётся в описании и исходных данных экспорта.
- Непонятный статус, некорректный JSON, отсутствующие/противоречивые шаги и некорректные package-state данные становятся `CORRUPTED`, а не пустым успешно откатываемым снимком.
- Экспорт включает всю историю, в том числе FAILED, legacy и непарсящиеся данные. Это диагностический экспорт, не обещание автоматического восстановления после импорта.

**Перед обновлением установленной v1:** сохраните её историю/экспорт и перезагрузите телефон. Не рассчитывайте, что недостоверные старые shell-откаты останутся доступными автоматически. Проверку миграции выполнять на тестовой копии/эмуляторе с тем же applicationId и ключом подписи, не на единственной рабочей установке.

## 6. Изменения потребителей и временные ограничения

- Ошибки строгих чтений обрабатываются ViewModel: busy-флаги сбрасываются, диагностика показывает необходимость проверки, а не здоровое значение по умолчанию.
- Fixer использует свежий диагностический verdict после записи, а не всегда `FIXED_ACTIVE`.
- Разовые maintenance-команды не выдаются за подтверждённый ремонт: проверяются ошибки, следующие команды после сбоя не запускаются, автоматического отката для них не обещается.
- Ошибка ART больше не показывает «bg-dexopt запущен», если fallback не запускался.
- В истории видны незавершённые/непроверенные статусы и ошибки; доступны повторные попытки допустимого восстановления.
- Оптимизатор не показывает неудачно прочитанные/начальные значения переключателей как фактические и не экспортирует их как профиль.
- Убрана подготовительная запись root-hosts и force-stop перед preflight карантина. Карантин теперь не делает эту незаписанную предварительную мутацию.
- Пустой результат ограниченного сканера не называется доказанно чистой системой; недоступный каталог CA не подтверждает отсутствие сертификатов.

**Произвольные `MutateCustomShell` сейчас отклоняются целиком до применения плана.** Это затрагивает, например, Game Mode, DeviceConfig, отдельные kernel/DPI/Doze/standby-tweaks, netpolicy и root-hosts. Смешанный пресет не применяется наполовину. Возвращать эти функции нужно как отдельные проверяемые операции либо явно необратимые сценарии, а не через константную строку `revertCommand`.

## 8. Ограничения и следующий шаг

1. Read → compare → write на Android не является атомарным CAS. Другой процесс может изменить ресурс между проверками; одинаковую повторную внешнюю запись по значению отличить нельзя. Mutex сериализует действия SwagDroid, не все приложения устройства.
2. Package-state привязан к UID/обновлению APK; AppOps пока ограничен пользователем/именем пакета/операцией и однозначным mode, не полным permission/UID-профилем или криптографической идентичностью приложения.
3. Kernel boot ID и данные Android считаются доверенными. Подменяющие их root-модули/скомпрометированная ОС не покрываются гарантией.
4. Нельзя обещать убийство всего дерева процессов или отмену уже принятой работы системного сервиса. Неопределённый исход остаётся блокирующим.
5. Полная матрица поддерживаемых OEM/SDK, работа после потери питания и производительность больших журналов ещё не проверены.
6. Не каждая старая диагностика является доказательством неисправности; покрытие сканеров и новая информационная архитектура остаются отдельными задачами.

**Следующим действием нужен штатный CI/Android-прогон этого среза, а не добавление новых функций поверх неподтверждённой сборки.** Затем smoke-матрица на тестовом устройстве: отказ/отзыв прав, смерть Shizuku, Root-таймаут, прерывание процесса, конфликт снимков, обновление APK пакета, secondary user/work profile, миграция v1 и сохранность legacy/повреждённых записей.
